cve_id:CVE-2026-41205
临时缓解措施
网络层面：网络隔离和访问控制： 为 token 创建端点添加 WAF 虚拟补丁：拦截仅携带 Bearer token 的新建凭据请求,依据触发过程，第 2 步的关键特征是：攻击者仅凭有效 API bearer token 调用 token 创建端点，而不是通过 passkey 支持的浏览器会话
配置层面：临时禁用 token creation endpoint：该漏洞仅在可调用的 token creation endpoint 存在时触发。临时缓解时，应在 API 网关、反向代理或服务路由配置中直接下线/拦截该接口，仅保留非相关接口访问。操作上，将该端点路由改为返回 403 或 404，并重新加载配置，使任何持有 bearer token 的请求都无法继续创建后继 token。 通过访问控制配置仅允许受信来源访问 token creation endpoint：若业务上暂时无法完全关闭该接口，则应在现有访问控制层对 token creation endpoint 单独收紧，仅允许明确的管理来源地址、管理网络或受控入口访问；其余来源统一拒绝。这样可直接降低“攻击者已获得有效 token 后远程调用该接口”的利用条件。实施时，在现有 ACL / allowlist / 路由鉴权规则中为该端点添加单独限制，然后重载相应配置。 临时关闭账户邀请相关功能：在“被盗 token 属于 account owner”时，攻击者可继续发起账户邀请并注册独立 passkey，形成持久控制。因此应在控制台/API 配置中临时禁用账户邀请/新增账户成员功能，或关闭对应接口的对外访问。操作上，将邀请相关端点在现有配置中设为不可用或仅限内部管理访问，以阻断从 owner token 到独立持久控制的后续路径。
权限层面：收紧并最小化 API token 权限范围（PoLP）：该漏洞必须先拿到一个有效 token 才能被利用，因此应立即减少高权限 token 的数量与能力。操作上：1）在 XERJ Console/API 凭据管理页面梳理全部现有 token；2）按账户/应用/自动化任务逐个核对其实际用途；3）删除不再使用、共享使用或用途不明的 token；4）将可拆分的高权限 token 改为仅保留必需权限的独立 token；5）禁止日常集成、脚本或个人使用 owner 级 token，仅将 owner 权限保留给极少数管理账户。重点检查是否存在可用于“账户邀请”“凭据创建”或其他管理操作的 token 被广泛分发。 强化 owner/管理员账户认证并减少其 token 暴露面：若攻击者获得 owner token，可继承完整管理权限并形成长期控制，因此应优先保护 owner 账户。操作上：1）为所有 owner/管理员账户强制启用并核验 passkey/MFA；2）关闭或停止共享管理员账户，改为个人实名管理账户；3）限制只有指定管理员才能登录控制台和执行账户邀请、凭据签发等高风险操作；4）检查现有自动化流程，确认未使用 owner 账户长期持有 API token；5）将 owner 账户仅用于必要管理，日常运维改用低权限账户。这样可降低高价值 token 被窃取后造成的继承性风险。 限制 token 的签发、保管与使用对象，避免“已认证权限”泄露：由于漏洞前提是攻击者已获取或截获有效 token，临时缓解重点应放在防止 token 落入无关人员或系统。操作上：1）仅向确有业务需要的用户、服务账户和集成发放 token；2）禁止通过聊天、工单、邮件、文档直接分享 token；3）将 token 保存在受访问控制的密钥库/机密管理位置，限制可读取人员；4）检查 CI/CD、脚本仓库、运维平台中谁可查看或导出机密，移除无关成员访问权限；5）对离职、转岗、外包和临时账号立即取消其控制台/API 访问与相关凭据读取权限。目标是把可被攻击者利用的“有效 token 持有面”压到最小。 对高风险管理操作启用人工审批或双人复核：漏洞利用链涉及“创建后继凭据”“发起账户邀请”等权限性操作，临时阶段可通过权限流程限制减少单个 token 被滥用后的影响。操作上：1）将账户邀请、管理员变更、新凭据创建等操作收敛到少数指定管理员；2）在组织流程中要求此类操作必须经过第二人审批或工单授权后执行；3）仅允许固定管理组成员访问相关控制台菜单/API 功能；4）定期复核该管理组名单，移除非必要成员。即使无法修改产品机制，也可通过管理权限收口与审批降低被窃 token 直接扩权的机会。 立即复核并收回不必要的长期有效 token 与高权限访问：该漏洞的危害在于派生 token 可持续存在，因此临时措施应优先降低现存高风险凭据基数。操作上：1）导出或查看当前所有 token 清单；2）优先排查 owner/管理员账户名下 token；3）对“长期未使用”“创建人不明”“用途不清”“属于共享账户”的 token 立即禁用或删除；4）同步复核哪些人员仍拥有控制台管理权限、邀请权限、凭据管理权限，撤销不再需要的访问；5）建立短周期（如每日/每周）人工复核，持续收紧权限面。这样可减少攻击者一旦拿到 token 后可继承的权限上限。
